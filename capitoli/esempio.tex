\section{OWASP Cloud Security Top 10}

Il portale AppSecMaster ha elaborato una propria classificazione dei dieci rischi più comuni e di maggiore impatto nei moderni ambienti cloud, ispirandosi ai principi promossi da OWASP in materia di sicurezza applicativa, che vanno dall'infrastruttura mal configurata alla scarsa visibilità delle risorse in esecuzione. Di seguito è riportata la lista delle principali problematiche individuate:
\begin{enumerate}
    \item \textbf{Security Misconfiguration} — Bucket di storage lasciati con permessi troppo permissivi o istanze di calcolo distribuite senza le dovute restrizioni restano tra le cause più frequenti di violazione dei dati in ambienti cloud.
    \item \textbf{Identity / Access Mismanagement} — Ruoli IAM assegnati con privilegi superiori a quelli effettivamente necessari, e mai rivisti dopo la configurazione iniziale, espongono i sistemi a un concreto rischio di escalation dei permessi.
    \item \textbf{Improper Secrets/Key Management} - Se chiavi API e credenziali vengono salvate in chiaro o incorporate nel codice sorgente, la loro compromissione può aprire un accesso laterale a più servizi collegati.
    \item \textbf{Insecure Network Segmentation} — Senza una reale separazione tra reti e ambienti diversi, un attaccante che viola un singolo componente può muoversi liberamente verso risorse più sensibili.
    \item \textbf{Injection / Input Validation Flaws in Cloud Services} — Le classiche vulnerabilità di injection assumono forme nuove nei contesti cloud-native, colpendo funzioni serverless, code di messaggi e gateway API dove i controlli sugli input non sono sempre applicati in modo uniforme.
    \item \textbf{Insecure Deserialization / API Exposure} — La gestione non sicura di dati serializzati, unita ad API interne prive di adeguati controlli di autenticazione o versionamento, costituisce un punto d'ingresso sfruttabile per eseguire codice non autorizzato.
    \item \textbf{Vulnerable Third-Party/Container Dependencies} — Librerie open source e immagini container non aggiornate accumulano vulnerabilità note, soprattutto quando le stesse basi vengono riutilizzate tra più progetti senza verifiche periodiche.
    \item \textbf{Improper Asset Inventory / Visibility} — Risorse cloud dimenticate o mai tracciate correttamente, incluse istanze abbandonate e servizi "ombra", sfuggono facilmente al controllo dei team di sicurezza.
    \item \textbf{Insufficient Logging / Monitoring} — Log distribuiti su decine di servizi diversi e privi di un formato coerente rendono difficile individuare per tempo un'intrusione in corso.
    \item \textbf{Unvalidated Redirects/Cloud Function Abuse} — Funzioni serverless eseguite con permessi troppo ampi, combinate a controlli insufficienti sui redirect, possono essere sfruttate per aggirare le restrizioni di accesso e ottenere un punto d'appoggio nascosto nell'infrastruttura.


    
\end{enumerate}

Tra le problematiche precedentemente descritte , il presente lavoro si basa in particolarme su Insecure Cloud Configurations e Insecure API Exposure per via della loro rilevanza diretta rispetto agli obiettivi del sistema sviluppato e alla loro frequente ricorrenza negli scenari di autorizzazione tipici delle architetture basate su API.

\subsection{Security Misconfiguration}
Una misconfiguration, in ambito cloud, nasce da un errore nella configurazione
di un servizio, di un prodotto o di una risorsa infrastrutturale: le
impostazioni di sicurezza predefinite non vengono irrobustite a
sufficienza, e questo lascia scoperto un fianco che con poco sforzo potrebbe
essere protetto. I numeri parlano chiaro: il documento ufficiale OWASP
riporta che il 90\% delle applicazioni testate è risultato vulnerabile ad
almeno una forma di misconfiguration~\cite{owasp2021a05}. Nella maggior
parte dei casi non c'è nulla di sofisticato dietro: è una dimenticanza,
un'impostazione lasciata di default, un permesso che nessuno ha mai rivisto.
Ed è proprio questo che la distingue da una vulnerabilità nel codice
applicativo — qui il problema non sta nella logica del software, ma in come
le risorse sono state predisposte.

Le forme più comuni in cui una misconfiguration si manifesta sono, in fondo,
poche e ricorrenti. Un bucket di storage lasciato accessibile pubblicamente,
quando avrebbe dovuto restare privato, è probabilmente la più diffusa: basta
una policy impostata male, magari copiata da un altro progetto senza troppa
attenzione. Un container che gira con privilegi di root, invece, espone il
sistema a un rischio diverso ma altrettanto concreto — se l'attaccante riesce
a comprometterlo, si ritrova con permessi ben oltre quelli che gli
servirebbero per fare danni. C'è poi il caso dei template
Infrastructure-as-Code scritti senza le dovute verifiche: un file Terraform
o CloudFormation che definisce una risorsa con permessi troppo ampi si porta
dietro lo stesso errore ogni volta che viene riutilizzato, replicandolo su
ambienti diversi senza che nessuno se ne accorga.

\paragraph{Un caso reale: il data breach Capital One}
Il caso Capital One del luglio 2019 resta probabilmente l'esempio più citato
di questa categoria di rischio. Un bucket Amazon S3 lasciato con permessi
troppo ampi permise a un'attaccante di sottrarre oltre 100 milioni di record
clienti, tra dati anagrafici, indirizzi e informazioni finanziarie
sensibili~\cite{sentinelone2025cloud}. Nessuna falla nella piattaforma
cloud era coinvolta: la responsabilità ricadeva interamente sulla
configurazione impostata dal cliente. Non a caso AWS, commentando
l'accaduto, ribadì che \textit{"Amazon S3 is secure by
default"}~\cite{news2023failures}, scaricando di fatto la colpa sulla
gestione dei permessi lato utente. Sul piano economico il conto fu salato:
80 milioni di dollari di multa dall'Office of the Comptroller of the
Currency, più 190 milioni versati per chiudere una class action. Capital One
dimostra bene quanto una semplice disattenzione in fase di configurazione
possa costare quanto, se non più di, un attacco costruito su un exploit
tecnicamente elaborato.

\bigskip

Episodi come questo spiegano perché, negli ultimi anni, le organizzazioni
abbiano iniziato ad affidarsi sempre meno alla revisione manuale delle
configurazioni e sempre più a strumenti automatizzati capaci di individuare
questo tipo di errori prima che vengano sfruttati. Una configurazione
insicura, del resto, raramente viene introdotta di proposito: emerge quasi
sempre da un template riutilizzato senza controllo, da un default mai
cambiato, da una revisione saltata per mancanza di tempo — fattori che un
controllo manuale sistematico difficilmente riesce a intercettare su larga
scala e con continuità.

Il documento ufficiale OWASP illustra questa categoria di rischio attraverso
quattro scenari esemplificativi~\cite{owasp2021a05}. Il primo riguarda
applicazioni di esempio dimenticate su un server di produzione, spesso
accompagnate da account amministrativi con credenziali mai modificate
rispetto ai valori predefiniti. Il secondo descrive un server su cui la
funzionalità di directory listing resta abilitata, consentendo a un
attaccante di risalire fino al codice sorgente tramite reverse engineering.
Il terzo riguarda messaggi di errore troppo dettagliati restituiti
dall'application server, capaci di esporre informazioni sull'infrastruttura
sottostante o versioni di componenti vulnerabili. Il quarto, infine,
riguarda permessi di condivisione predefiniti di un cloud service provider
lasciati aperti ad altri utenti su Internet, con conseguente esposizione di
dati sensibili archiviati nello storage cloud.

Fra i quattro scenari, due ricadono nel perimetro del sistema presentato in questo lavoro e due ne restano fuori.


\section{API Security Risks}

Le API oggi fanno gran parte del lavoro che una volta faceva il sito web
stesso: non restituiscono una pagina pensata per essere letta da una
persona, ma dati grezzi destinati a un'altra app, a un altro servizio, a un
sistema che poi decide cosa farne. Lo schema delle richieste è prevedibile,
gli endpoint espongono operazioni precise su risorse precise. Per un
attaccante questo significa meno lavoro di interpretazione: non deve capire
un'interfaccia grafica, gli basta osservare come sono costruite le chiamate.

OWASP mantiene, accanto al Top 10 per le applicazioni web, una
classificazione separata dedicata alle API. Alcune categorie compaiono in
entrambe le liste — la misconfiguration, il broken access control — ma buona
parte dei rischi specifici delle API riguarda un livello che il Top 10
generale non copre: l'autorizzazione su singoli oggetti, proprietà,
funzioni. Un'applicazione web tradizionale filtra cosa mostrare all'utente;
un'API deve filtrare cosa restituire nella risposta. La differenza sembra
minima, ma è da lì che nascono molte delle vulnerabilità trattate in
questa sezione.

Le dieci categorie che compongono l'edizione 2023 riflettono questa logica: non
rischi generici, ma rischi legati al modo specifico in cui un'API espone dati e
funzionalità. Di seguito la lista completa, in ordine di gravità
secondo OWASP~\cite{owasp2023apitop10}:
\begin{enumerate}
  \item \textbf{API1:2023 -- Broken Object Level Authorization (BOLA)} — un
  endpoint accetta l'ID di una risorsa senza verificare che chi lo richiede
  abbia davvero il diritto di accedervi; basta cambiare un numero nell'URL
  per leggere dati altrui.

  \item \textbf{API2:2023 -- Broken Authentication} — meccanismi di
  autenticazione implementati male, token che non scadono mai, o password
  recuperabili senza controlli sufficienti.

  \item \textbf{API3:2023 -- Broken Object Property Level Authorization} —
  qui il problema non è accedere alla risorsa sbagliata, ma vedere o
  modificare campi che non dovrebbero essere esposti o scrivibili da quel
  particolare utente.

  \item \textbf{API4:2023 -- Unrestricted Resource Consumption} — assenza di
  limiti su chiamate, dimensione dei payload o uso di risorse computazionali,
  con conseguenze che vanno dal semplice rallentamento a un vero e proprio
  denial of service.

  \item \textbf{API5:2023 -- Broken Function Level Authorization} — un
  utente normale riesce a invocare funzioni riservate agli amministratori,
  semplicemente perché il controllo sui permessi manca a livello di endpoint
  o di metodo HTTP.

  \item \textbf{API6:2023 -- Unrestricted Access to Sensitive Business
  Flows} — la singola richiesta può essere anche legittima, ma se ripetuta
  migliaia di volte automatizza un abuso della logica di business (es.
  acquisto massivo di biglietti, creazione automatica di account).

  \item \textbf{API7:2023 -- Server Side Request Forgery (SSRF)} — l'API
  accetta un URL fornito dall'utente e lo interroga senza validarlo,
  permettendo di raggiungere risorse interne altrimenti non accessibili
  dall'esterno.

  \item \textbf{API8:2023 -- Security Misconfiguration} — header di
  sicurezza mancanti, CORS troppo permissivo, ambienti di debug ancora
  attivi in produzione: stessa famiglia di errori vista nel capitolo
  precedente, qui applicata allo strato applicativo.

  \item \textbf{API9:2023 -- Improper Inventory Management} — endpoint
  vecchi, versioni deprecate o ambienti di staging dimenticati online, mai
  rimossi né monitorati, restano comunque raggiungibili da chi li trova.

  \item \textbf{API10:2023 -- Unsafe Consumption of APIs} — la vulnerabilità
  non nasce nell'API stessa, ma nella fiducia cieca riposta nei dati
  restituiti da API di terze parti integrate nel sistema.
\end{enumerate}

Tra le dieci categorie appena elencate la prima merita un'attenzione diversa
dalle altre: non tanto per la posizione in classifica, quanto per ciò che
rappresenta, cioè un controllo di accesso che manca proprio dove ci si
aspetterebbe fosse più solido, sulla singola risorsa richiesta. È il tipo di
errore che si insinua facilmente in un endpoint scritto in fretta e che, allo
stesso tempo, può esporre porzioni estese della base dati di un sistema con una
richiesta HTTP modificata di poco. La sottosezione seguente lo esamina nel
dettaglio: come si manifesta, da quali cause nasce e con quali misure lo si
previene.

\subsection{API1:2023 -- Broken Object Level Authorization}

\paragraph{Definizione e collocazione}

La Broken Object Level Authorization (BOLA) si manifesta quando un'applicazione, pur autenticando
correttamente l'utente che effettua una richiesta, non verifica se quello stesso utente abbia
effettivamente il diritto di accedere all'oggetto specifico
richiesto~\cite{owasp2023api1}.

Un'interfaccia di programmazione applicativa espone tipicamente un insieme di risorse --- utenti,
ordini, documenti, transazioni --- identificabili singolarmente attraverso un riferimento univoco.
L'accesso a tali risorse presuppone due verifiche concettualmente distinte, spesso confuse nella
pratica implementativa: l'autenticazione, che accerta l'identità del soggetto che effettua la
richiesta, e l'autorizzazione, che stabilisce se quel soggetto, una volta identificato, abbia il
diritto di operare su una specifica risorsa.

Un utente autenticato correttamente non è, per definizione, un utente autorizzato ad accedere a
qualunque oggetto gestito dal sistema. Questa distinzione, apparentemente elementare, è proprio il
punto in cui molte implementazioni falliscono: il possesso di credenziali valide viene talvolta
considerato --- implicitamente, nel disegno del codice --- condizione sufficiente per l'accesso a
una risorsa, quando in realtà rappresenta soltanto la premessa per una verifica ulteriore, relativa
alla relazione specifica tra quell'utente e quell'oggetto.

\paragraph{Funzionamento delle API e ruolo degli identificatori di risorsa}

Le API REST, e in misura diversa quelle basate su GraphQL, espongono le risorse attraverso
identificatori che compaiono nel percorso della richiesta, nei parametri di query, nel corpo del
messaggio o negli header. Un endpoint come \texttt{GET /api/orders/482} restituisce, nella maggior
parte delle implementazioni, l'oggetto ordine identificato dal valore 482, indipendentemente dal
fatto che tale valore sia un intero progressivo, un UUID o un altro tipo di riferimento.

La gestione di una richiesta di questo tipo comporta, lato server, due passaggi distinti: la
risoluzione dell'identificatore in un oggetto concreto, tramite interrogazione del database o di un
servizio dati, e il controllo che l'utente autenticato abbia diritto di accesso a quell'oggetto
specifico. Il primo passaggio è quasi sempre implementato correttamente, poiché è indispensabile al
funzionamento stesso dell'endpoint; il secondo, non avendo un effetto visibile quando manca, viene
più facilmente trascurato o dato per scontato in fase di sviluppo.

Va osservato che l'endpoint, in questo scenario, non è di per sé vietato all'utente: la sua
configurazione di ruoli e permessi lo autorizza a invocare quella funzione API. Questo distingue
concettualmente BOLA da un'altra categoria della stessa famiglia, la Broken Function Level
Authorization (BFLA), in cui è l'accesso alla funzione stessa a non essere autorizzato. In BOLA la
funzione è legittima; il problema riguarda esclusivamente quale istanza dell'oggetto venga
restituita o modificata.

\paragraph{Meccanismo dell'attacco}

Lo sfruttamento di una vulnerabilità BOLA non richiede, nella maggior parte dei casi, strumenti
sofisticati né la compromissione di credenziali altrui. È sufficiente disporre di un account
legittimo sul sistema bersaglio. Il percorso tipico dell'attacco segue una sequenza riconoscibile:
l'utente accede al proprio account, richiede una propria risorsa attraverso l'interfaccia normale
dell'applicazione e osserva, tramite gli strumenti di sviluppo del browser o un proxy di
intercettazione, l'identificatore associato a quella risorsa nella richiesta sottostante.

A questo punto l'identificatore viene sostituito con un altro valore plausibile per lo stesso
schema --- un intero vicino, nel caso di sequenze numeriche, oppure un valore ottenuto per
enumerazione più sistematica quando lo schema lo consente --- e la richiesta viene reinviata con lo
stesso token di autenticazione, valido e non modificato. Ad esempio:

\begin{verbatim}
GET /api/orders/483 HTTP/1.1
Host: api.example.com
Authorization: Bearer <token_utente_A>
\end{verbatim}

dove 483 non è l'ordine appartenente al titolare del token, ma un identificatore vicino a quello
osservato in precedenza durante il normale utilizzo dell'applicazione. La richiesta è, dal punto di
vista del protocollo, del tutto regolare: cambia soltanto il valore del parametro. Che la
risposta contenga davvero i dati di un altro utente dipende da un unico fattore, ripreso nel
paragrafo seguente: se il server confronti o meno l'identità del chiamante con il proprietario
effettivo dell'oggetto.

\paragraph{Esempio applicativo}

Si consideri il caso concreto della risorsa \texttt{/api/orders/\{id\}}, utilizzata per recuperare
i dettagli di un ordine. Una richiesta legittima, effettuata dal proprietario dell'ordine 482, ha
la forma:

\begin{verbatim}
GET /api/orders/482 HTTP/1.1
Host: api.example.com
Authorization: Bearer <token_utente_A>
\end{verbatim}

e produce una risposta simile alla seguente:

\begin{verbatim}
HTTP/1.1 200 OK
Content-Type: application/json

{
  "order_id": 482,
  "customer_id": 1041,
  "items": ["..."],
  "shipping_address": "..."
}
\end{verbatim}

La richiesta modificata introdotta nel paragrafo precedente, diretta all'ordine 483 e appartenente
a \texttt{customer\_id} 1078, viene gestita da un'implementazione vulnerabile allo stesso modo:
l'identificatore viene estratto dal percorso, la tabella corrispondente viene interrogata, il
risultato viene restituito. In nessun punto di questo flusso il valore di \texttt{customer\_id}
restituito viene confrontato con l'identità associata al token presente nell'header
\texttt{Authorization}. La risposta, di conseguenza, è ancora un \texttt{200 OK}, questa volta con
i dati di un ordine che non appartiene al chiamante.

Il punto critico non è la struttura della richiesta, identica nei due casi, ma l'assenza di un
confronto esplicito fra utente autenticato e risorsa richiesta. Un'implementazione corretta
dovrebbe, prima di restituire l'oggetto, verificare che il \texttt{customer\_id} dell'ordine
coincida con l'identità del chiamante --- o che quest'ultimo disponga di un diritto di accesso
esplicitamente concesso su quella risorsa --- e restituire, in caso contrario, un errore di
autorizzazione: tipicamente \texttt{403 Forbidden}, oppure \texttt{404 Not Found} quando si
preferisce non rivelare l'esistenza della risorsa a chi non ne ha diritto.

\paragraph{Cause e meccanismi tecnici tipici}

L'assenza di un controllo di autorizzazione a livello di oggetto è la causa immediata di ogni
istanza di BOLA, ma raramente costituisce una scelta progettuale deliberata. Più spesso deriva da
alcune condizioni che meritano di essere analizzate singolarmente.

La prima riguarda la sovrapposizione concettuale tra autenticazione e autorizzazione nella fase di
implementazione. Un endpoint protetto da un middleware di autenticazione, che verifica la validità
del token e ne estrae l'identità, può apparire sicuro a chi lo sviluppa, inducendo a trascurare la
necessità di un controllo ulteriore specifico per l'oggetto acceduto. Il middleware risponde alla
domanda ``chi sta chiamando?'', non a ``questo chiamante ha diritto su questo oggetto?''.

Una seconda causa è la fiducia implicita nei parametri forniti dal client. Alcune implementazioni
derivano l'identità del proprietario di una risorsa dallo stesso identificatore fornito nella
richiesta, oppure presuppongono che, poiché l'interfaccia utente dell'applicazione non espone mai
identificatori altrui, un client ``onesto'' non li invierebbe mai. Questa assunzione ignora che un
client HTTP può essere costruito o modificato arbitrariamente da chi effettua la richiesta,
indipendentemente dall'interfaccia grafica ufficiale.

Un terzo fattore è rappresentato da controlli di autorizzazione implementati in modo incompleto o
incoerente tra i diversi endpoint di una stessa API. È relativamente comune riscontrare verifiche
corrette sull'operazione di cancellazione di una risorsa e verifiche assenti sull'operazione di
lettura o aggiornamento della medesima risorsa, poiché ciascun endpoint viene sviluppato e
sottoposto a revisione in momenti diversi, con criteri non sempre uniformi. La crescita organica di
un'API nel tempo, con l'aggiunta progressiva di nuovi endpoint da parte di sviluppatori diversi,
tende ad amplificare questa disomogeneità.

Una causa più strutturale riguarda infine la gestione delle relazioni tra utenti e risorse nel
modello dati. Quando tale relazione non è rappresentata in modo esplicito e interrogabile --- ad
esempio tramite una chiave esterna diretta tra la tabella degli utenti e quella delle risorse, o
tramite un livello di autorizzazione centralizzato --- ogni endpoint deve reimplementare
autonomamente la logica di verifica, e questo aumenta la probabilità che qualche percorso venga
trascurato.

\paragraph{Impatto}

L'impatto di una vulnerabilità BOLA dipende dalla natura della risorsa esposta, ma incide
tipicamente su più proprietà di sicurezza contemporaneamente. Sul piano della riservatezza,
l'accesso non autorizzato a un oggetto consente la lettura di dati che dovrebbero rimanere
riservati al proprietario legittimo: informazioni personali, dettagli finanziari, contenuti
sanitari, comunicazioni private, a seconda del dominio applicativo.

Quando l'endpoint vulnerabile consente anche operazioni di scrittura, l'impatto si estende
all'integrità delle risorse: un attaccante può modificare dati appartenenti ad altri utenti,
alterare lo stato di un ordine, cambiare le impostazioni di un account che non gli appartiene. Se
l'operazione esposta è una cancellazione, la conseguenza diventa la perdita di disponibilità della
risorsa per il legittimo proprietario.

Un aspetto che distingue BOLA da molte altre classi di vulnerabilità è la sua natura
sistematicamente ripetibile: una volta individuato un endpoint privo del controllo appropriato, lo
stesso schema di attacco può essere applicato a un numero elevato di identificatori, trasformando
quella che sembra una singola falla puntuale in un canale di accesso a porzioni estese della base
dati.

Il rischio assume connotati particolari negli ambienti multi-tenant e cloud, dove più clienti
condividono la stessa infrastruttura applicativa e la separazione tra i rispettivi dati dipende
interamente dalla correttezza della logica di autorizzazione, non da una separazione fisica delle
risorse. In un simile contesto, una singola vulnerabilità BOLA non compromette soltanto i dati di
un utente, ma può erodere il confine logico tra tenant distinti, con implicazioni che vanno oltre
il singolo incidente e toccano la fiducia complessiva riposta nell'infrastruttura condivisa.

\paragraph{Mitigazione}

La prevenzione di BOLA richiede che ogni accesso a una risorsa identificata da un parametro
fornito dal client sia accompagnato da una verifica esplicita del diritto dell'utente su quello
specifico oggetto, eseguita interamente lato server. Nessuna informazione proveniente dal client,
incluso l'identificatore stesso della risorsa, può essere considerata prova di autorizzazione:
l'identificatore indica quale oggetto viene richiesto, non chi ha diritto di accedervi.

Un principio applicabile in modo trasversale è quello del \textit{least privilege}, secondo cui un soggetto
dovrebbe disporre soltanto dei permessi strettamente necessari a svolgere le proprie funzioni,
senza margini di accesso più ampi per comodità implementativa. Applicato al livello oggetto,
questo si traduce nella necessità di associare esplicitamente ogni utente, o ruolo, alle risorse su
cui ha effettivamente diritto di operare, evitando che l'accesso derivi da assunzioni implicite
sulla struttura delle richieste.

Dal punto di vista architetturale, è preferibile centralizzare la logica di autorizzazione in un
livello comune --- un modulo, un middleware o un servizio dedicato --- piuttosto che
reimplementarla in modo indipendente in ciascun endpoint. Questa scelta non elimina la necessità di
applicare il controllo in ogni punto di accesso, ma riduce la probabilità che errori o
dimenticanze locali producano percorsi non protetti, e semplifica la verifica di coerenza tra le
diverse funzioni esposte dall'API.

La coerenza dei controlli tra operazioni di lettura, scrittura e cancellazione sulla stessa risorsa
merita infine attenzione specifica: la protezione di un'operazione non implica automaticamente la
protezione delle altre, ed è in questa asimmetria che si annida buona parte delle istanze reali di
BOLA.

Le sottosezioni seguenti trattano in forma più sintetica le restanti categorie della OWASP API
Security Top 10, a partire da API2:2023.

\newpage
\subsection{API2:2023 -- Broken Authentication}

\paragraph{Definizione e collocazione}
Broken Authentication occupa la seconda posizione della classificazione OWASP e si colloca concettualmente a monte di BOLA: mentre quest'ultima riguarda il controllo sull'accesso a uno specifico dato o risorsa, Broken Authentication compromette la capacità stessa del sistema di stabilire con certezza l'identità di chi effettua la richiesta. Un fallimento in questa fase rende vano qualsiasi controllo successivo, poiché un meccanismo di autorizzazione perde ogni efficacia se l'identità su cui si fonda può essere falsificata o aggirata~\cite{owasp2023api2}.
A differenza di altre categorie più circoscritte, questa voce raggruppa un insieme eterogeneo di debolezze nei processi di verifica dell'identità: dalla gestione poco attenta dei token di sessione all'assenza di vincoli sul numero di tentativi di accesso consentiti. Un esempio comune riguarda i messaggi di risposta del server: se il sistema indica esplicitamente quale dei due campi, nome utente o password, sia errato, fornisce involontariamente all'attaccante una conferma sull'esistenza di quell'account. Parallelamente, l'assenza di limitazioni sulla frequenza delle richieste lascia l'interfaccia di login esposta ad attacchi automatizzati volti a indovinare le credenziali su larga scala.

\paragraph{Cause e meccanismi tecnici tipici}

Spesso queste problematiche nascono dal tentativo di implementare soluzioni di autenticazione proprietarie o non standard. Come evidenziato dalla documentazione OWASP, strumenti come le API key o protocolli di autorizzazione come OAuth vengono talvolta impiegati impropriamente per identificare gli utenti in scenari per cui non sono stati progettati, creando falle strutturali~\cite{owasp2023api2}.
Un ulteriore fattore critico è la mancanza di controlli sul volume dei tentativi di accesso. Endpoint di autenticazione e flussi di recupero password privi di rate limiting risultano vulnerabili ad attacchi in cui elenchi di credenziali già compromesse altrove vengono provati in massa, sfruttando la tendenza diffusa a riutilizzare le medesime password su più servizi~\cite{owasp2026credential}.
Infine, la gestione dei token di sessione (come i JSON Web Token, o JWT) introduce ulteriori insidie: errori nella convalida della firma crittografica, chiavi di cifratura deboli, mancato controllo dei tempi di scadenza o assenza di meccanismi di revoca immediata permettono a un attaccante di forgiare token validi o di continuare a utilizzare credenziali che dovrebbero essere già decadute~\cite{rfc8725}.

\paragraph{Impatto}

L'impatto di Broken Authentication è per sua natura sistemico: assumendo il controllo dell'identità di un utente, l'attaccante ne eredita tutti i privilegi operativi senza che il backend possa distinguere le azioni legittime da quelle malevole~\cite{owasp2023api2}. Ciò può tradursi non solo nell'accesso a dati riservati, ma anche nella manomissione dei parametri di sicurezza dell'account (come la modifica dell'indirizzo di recupero), trasformando un'intrusione temporanea nella perdita definitiva del profilo.

\paragraph{Mitigazione}

La contromisura principale consiste nell'affidarsi a standard industriali consolidati e a librerie verificate, evitando soluzioni ``fai-da-te'' per la gestione di token e password~\cite{nist2025sp80063b}. A livello applicativo e infrastrutturale è indispensabile introdurre politiche di rate limiting dedicate e restrittive sugli endpoint di login, adottare l'autenticazione a più fattori (MFA) dove possibile e imporre una nuova conferma delle credenziali prima di eseguire modifiche critiche sul profilo utente~\cite{owasp2026authentication}.

\paragraph{Rilevabilità}

Sul piano della rilevabilità l'analisi automatica si divide in due direttrici, a seconda della natura del difetto.
\begin{enumerate}
\item \textbf{Analisi dei token e della crittografia.} Le debolezze che riguardano i JWT e gli altri formati di sessione dipendono da regole deterministiche e ben definite, come la mancata verifica della firma o l'uso di algoritmi insicuri. Gli strumenti riescono quindi a individuarle con buona affidabilità, sia analizzando staticamente il codice sorgente per intercettare configurazioni errate delle librerie crittografiche, sia generando dinamicamente token manipolati per verificare se il backend li accetti~\cite{yang2025jwteemo,xu2023jwtkey}.
\item \textbf{Flussi di autenticazione e abusi comportamentali.} L'assenza di rate limiting e l'esposizione a tentativi di accesso massivi richiedono invece un monitoraggio a runtime: più che da un'ispezione sintattica del codice, queste carenze emergono dall'analisi dinamica del traffico o dai registri di sistema, dove si manifestano come picchi anomali di richieste fallite concentrate in brevi finestre temporali~\cite{owasp2026credential}.
\end{enumerate}

\subsection{API3:2023 -- Broken Object Property Level Authorization}

\paragraph{Definizione e collocazione}

La \textit{Broken Object Property Level Authorization} (BOPLA) identifica una classe di vulnerabilità nella quale i controlli di autorizzazione applicati alle API non considerano adeguatamente le singole proprietà degli oggetti gestiti dall'applicazione. Il problema non riguarda quindi soltanto la possibilità per un utente di accedere a un determinato oggetto, ma anche quali attributi di quell'oggetto possa effettivamente leggere o modificare~\cite{owasp2023apitop10}.

La distinzione rispetto alla \textit{Broken Object Level Authorization} (BOLA) è rilevante. Nel caso di BOLA, il controllo di autorizzazione fallisce a livello dell'oggetto: un utente riesce, per esempio, ad accedere a una risorsa appartenente a un altro utente manipolando l'identificativo della risorsa. Nel caso di BOPLA, invece, l'utente può avere legittimamente accesso all'oggetto, ma ottenere o modificare proprietà che non rientrano nei suoi privilegi. L'oggetto, quindi, non costituisce necessariamente la risorsa a cui viene negato l'accesso; è una sua specifica proprietà a essere esposta o manipolabile senza un'adeguata autorizzazione.

Il rischio è particolarmente rilevante nelle API REST, dove è frequente che un endpoint restituisca direttamente la rappresentazione serializzata di un oggetto. Una struttura interna composta da numerosi attributi può così diventare, in assenza di una selezione esplicita, il corpo stesso della risposta inviata al client.

\paragraph{Cause e meccanismi tecnici tipici}

Una delle cause più comuni è la sovrapposizione tra il modello utilizzato internamente dall'applicazione e quello esposto attraverso l'API. Un oggetto memorizzato nel database può contenere, ad esempio, proprietà quali \texttt{id}, \texttt{name}, \texttt{email}, \texttt{role} e \texttt{internalStatus}. Non tutte queste proprietà hanno però la stessa finalità né devono necessariamente essere accessibili allo stesso insieme di utenti.

Un'implementazione che serializza automaticamente l'intero oggetto può produrre una risposta contenente anche attributi che il client non dovrebbe conoscere. In questo caso il problema non deriva necessariamente da un accesso non autorizzato all'oggetto, ma dal fatto che l'API non applica una politica distinta alle proprietà che lo compongono. L'interfaccia grafica potrebbe nascondere determinati campi, ma ciò non costituisce una misura di sicurezza: il contenuto della risposta HTTP rimane osservabile dal client e può essere analizzato direttamente.

Un secondo meccanismo riguarda le operazioni di scrittura. Framework e librerie possono consentire il \textit{binding} automatico dei parametri ricevuti dal client verso gli attributi di un oggetto applicativo. Se il server accetta un payload come:

\begin{verbatim}
{
  "name": "Mario",
  "email": "mario@example.com"
}
\end{verbatim}

un attaccante può provare ad aggiungere proprietà che non erano previste dal normale flusso applicativo:

\begin{verbatim}
{
  "name": "Mario",
  "email": "mario@example.com",
  "role": "admin"
}
\end{verbatim}

Se il campo \texttt{role} viene accettato e aggiornato senza un controllo specifico, l'utente può modificare una proprietà interna che dovrebbe essere gestita esclusivamente dal sistema. Lo stesso principio può riguardare attributi quali \texttt{isAdmin}, \texttt{approved}, \texttt{price} o \texttt{ownerId}, a seconda del modello utilizzato dall'applicazione.

Il problema può quindi manifestarsi in due direzioni differenti: lettura non autorizzata di proprietà e modifica non autorizzata di proprietà. Nel primo caso l'attaccante osserva informazioni che non dovrebbe ricevere; nel secondo riesce a influenzare direttamente lo stato dell'applicazione attraverso attributi che non dovrebbero essere controllabili dal client.

\paragraph{Impatto}

L'impatto di una vulnerabilità BOPLA dipende principalmente dal tipo di proprietà coinvolta e dalle funzioni che la utilizzano. La semplice esposizione di un attributo può comportare una violazione della riservatezza, mentre la possibilità di modificarlo può compromettere l'integrità dei dati o il funzionamento dell'applicazione.

Nel caso di proprietà contenenti informazioni personali, finanziarie o relative all'organizzazione interna del sistema, l'esposizione può determinare una divulgazione di dati a soggetti non autorizzati. La possibilità di modificare determinate proprietà può invece portare alla perdita o alla corruzione dei dati. In situazioni più critiche, una proprietà utilizzata nei meccanismi di autorizzazione o nella gestione dello stato dell'account può essere sfruttata per ottenere un'escalation dei privilegi o contribuire alla compromissione dell'account. La gravità della vulnerabilità dipende quindi dal significato che quella proprietà assume all'interno dell'applicazione, più che dal meccanismo che ne consente l'accesso.

\paragraph{Mitigazione}

La mitigazione di BOPLA richiede che l'autorizzazione venga applicata non soltanto all'endpoint o all'oggetto, ma anche alle proprietà che possono essere restituite o modificate. La prima misura consiste quindi nel definire esplicitamente quali attributi ogni endpoint può esporre e quali possono essere accettati in input.

Per le risposte è preferibile evitare i meccanismi di serializzazione automatica, che restituiscono l'oggetto così com'è rappresentato internamente, e selezionare invece le proprietà necessarie alla singola operazione.

Per le operazioni di scrittura è necessario limitare esplicitamente gli attributi modificabili dal client. Una tecnica comune consiste nell'utilizzare una \textit{whitelist} delle proprietà ammesse, evitando che il payload venga associato automaticamente a tutti gli attributi dell'oggetto.

\paragraph{Rilevabilità}

La rilevazione di BOPLA si articola in due verifiche distinte, corrispondenti alle due direzioni in cui una proprietà può attraversare il confine fra client e server.

La prima riguarda le proprietà esposte in risposta a una richiesta legittima, e si riduce al confronto fra gli attributi effettivamente restituiti e quelli previsti per il ruolo o il contesto dell'utente. È la verifica più diretta, perché l'evidenza è contenuta nella risposta stessa.

La seconda riguarda le proprietà accettate in ingresso, ed è più onerosa perché il server non le dichiara. Individuarle richiede di modificare il payload delle richieste, eventualmente ricorrendo a tecniche di fuzzing per scoprire attributi non documentati, e di verificare poi se il server ne recepisca effettivamente il valore.

Le due verifiche non sono sostituibili l'una con l'altra: un'API può accettare in input una proprietà sensibile che non restituisce mai, oppure restituire dati riservati senza consentirne la modifica. Un'analisi che si limitasse a una sola direzione lascerebbe scoperta metà del problema.

\subsection{API4:2023 -- Unrestricted Resource Consumption}
\label{subsubsec:api4}

\paragraph{Definizione e collocazione}

Ogni richiesta servita da un'API consuma risorse: banda, CPU, memoria, storage
e, con frequenza crescente, servizi a pagamento di terze parti. La categoria
API4:2023 raccoglie i casi in cui almeno uno dei limiti che dovrebbero governare
quel consumo è assente o dimensionato male, fra cui i timeout di esecuzione, la
memoria allocabile e il numero di processi~\cite{owasp2023api4}.

La collocazione richiede un chiarimento, perché il consumo di risorse non è il
difetto di una funzione specifica ma una proprietà trasversale di qualunque
endpoint, e i limiti che lo governano sono la difesa in profondità di altre
categorie. Le quattro relazioni che contano sono riassunte nella
Tabella~\ref{tab:api4_relazioni}.

\hline
\textbf{Categoria} & \textbf{Punto di contatto con API4} & \textbf{Elemento distintivo} \\
\hline
API2 & Endpoint di autenticazione con limiti più severi; batching che aggira il rate limiting & Bene protetto: segretezza della credenziale contro disponibilità e costo \\
API6 & Automazione di richieste legittime; l'attacco distribuito elude il throttling per IP & Danno sul piano del business, impatto tecnico non atteso \\

\label{tab:api4_relazioni}
\end{table}

\paragraph{Cause e meccanismi tecnici tipici}

La radice comune è un'asimmetria: produrre una richiesta costa al client quasi
nulla, servirla può costare al server una quantità che cresce in funzione di
parametri che il client controlla. Finché quella funzione di costo non ha un
limite superiore, l'API resta esposta. Quattro meccanismi meritano distinzione,
perché ciascuno richiede una difesa diversa.

Il primo è il volume puro, che OWASP giudica sfruttabile senza competenze
particolari~\cite{owasp2023api4}. Più insidiosa dell'assenza totale del limite è
però la sua presenza in una sola dimensione: un tetto per indirizzo IP cade
contro un attacco distribuito, uno per endpoint non intercetta il batching, uno
per utente autenticato lascia scoperti gli endpoint anonimi di registrazione e
recupero credenziali.

Il secondo riguarda i parametri che governano la dimensione della risposta: un
endpoint paginato che accetta \texttt{limit=100000} trasforma una chiamata in
una scansione completa della tabella, ed è per questo che OWASP ne prescrive la
validazione lato server~\cite{owasp2023api4}.

Il terzo moltiplica le operazioni dentro una richiesta sola: nello scenario
GraphQL un'API limita la frequenza sull'endpoint e la dimensione delle immagini,
ma non le mutazioni aggregate, e centinaia di \texttt{uploadPic} in un unico
batch saturano la memoria aggirando entrambe le protezioni~\cite{owasp2023api4}.
Cha et~al.\ mostrano che nel caso peggiore una query impone un lavoro
esponenziale~\cite{cha2020graphql}, e lo stesso vale per ogni endpoint REST che
accetti un array di operazioni senza limitarne la cardinalità.

Il quarto dipende dal costo algoritmico di una singola
richiesta~\cite{crosby2003algorithmic}: l'istanza più diffusa è il ReDoS, che
Staicu e Pradel documentano nei server JavaScript, dove il thread singolo rende
una richiesta sufficiente a congelare il processo~\cite{staicu2018redos}. Vi si
aggiunge la causa che l'edizione 2023 porta in primo piano, l'assenza di soglie
di spesa verso i fornitori esterni, dove la risorsa non è computazionale ma
economica~\cite{owasp2023api4}.

Che limiti tanto semplici manchino dipende da due fatti. Il primo è che possono
risiedere nel framework, nel proxy, nel gateway o presso il fornitore cloud, e
quando ogni livello presume che se ne occupi un altro non se ne occupa nessuno.
Il secondo è che la loro assenza non produce errori: un endpoint privo di limiti
supera ogni test funzionale.

\paragraph{Impatto}

L'esito immediato è il denial of service per esaurimento, che CWE-770 enumera
come conseguenza principale sulla disponibilità~\cite{cwe770}. Il punto di
rottura è però la logica applicativa anziché la banda, e il traffico richiesto
può essere di ordini di grandezza inferiore: una sola richiesta ReDoS o un solo
batch GraphQL bastano, e nessuna difesa perimetrale basata sul volume li
riconosce come anomali.

L'edizione 2023 dà pari dignità alla dimensione economica, e due dei tre scenari
non producono alcuna interruzione: un recupero password che invia SMS a 0,05
dollari l'uno, invocato decine di migliaia di volte, e un file di dimensione
superiore alla soglia oltre la quale la cache smette di intervenire, con la
fattura mensile che passa da circa 13 a circa 8\,000
dollari~\cite{owasp2023api4}.

\paragraph{Mitigazione}

Nessun livello basta da solo. I limiti fisici su memoria, CPU e processi sono
affidati da OWASP alle piattaforme che li rendono
dichiarativi~\cite{owasp2023api4}: una difesa di ultima istanza, che non
impedisce l'abuso ma lo confina.

All'ingresso dei dati la regola è dichiarare una dimensione massima per ogni
parametro e payload, soprattutto per quelli che governano il numero di record
restituiti~\cite{owasp2023api4}. Il contratto OpenAPI è il luogo naturale per
esplicitare quei vincoli, che così diventano verificabili da uno strumento.

Sul piano delle interazioni il rate limiting va tarato per endpoint e affiancato
da un limite sulle esecuzioni della singola operazione per utente, che il
conteggio delle chiamate non cattura~\cite{owasp2023api4}; sugli endpoint di
autenticazione si irrigidisce~\cite{owasp2023api2,nist2025sp80063b}. HTTP
fornisce il codice \texttt{429}~\cite{rfc6585}, di cui l'IETF sta
standardizzando i campi complementari~\cite{polli2026ratelimit}. NIST colloca il
throttling nel gateway anziché nel singolo servizio~\cite{nist2019sp800204}:
scelta corretta purché ogni host esposto stia dietro quel gateway, mentre il
limite scritto nel codice viaggia con l'applicazione in ogni ambiente.

Per la famiglia algoritmica servono timeout su ogni operazione lunga e, per il
ReDoS, motori a tempo lineare~\cite{staicu2018redos}; per GraphQL, l'analisi
statica del costo di una query prima di eseguirla~\cite{cha2020graphql}. Per la
dimensione economica OWASP prescrive soglie di spesa o allarmi di
fatturazione~\cite{owasp2023api4}.

\paragraph{Rilevabilità}

Le due fonti primarie sembrano contraddirsi. OWASP giudica facile la
rilevabilità, perché richieste con parametri di dimensione crescente e
l'osservazione di stato, tempo e lunghezza della risposta bastano a far emergere
il problema~\cite{owasp2023api4}; CWE-770 giudica invece di utilità limitata
l'analisi statica per le allocazioni prive di limite~\cite{cwe770}. La
contraddizione è apparente, perché le due fonti non parlano dello stesso
osservatore: OWASP descrive un tester in black box, CWE uno strumento che legge
il codice.

Sul versante dinamico l'evidenza è consolidata: CWE-770 riconosce efficaci le
tecniche basate sulla generazione di molte richieste in un intervallo
breve~\cite{cwe770}, e Antunes, Neves e Veríssimo sono fra i primi a proporre un
rilevamento sistematico per iniezione di carico~\cite{antunes2008resource}. Il
metodo OWASP è in sostanza un test differenziale, e ha un vantaggio decisivo su
ogni analisi del codice: osserva il sistema nel suo insieme, e vede quindi il
limite ovunque sia applicato. Vede però solo l'host che interroga.

Sul versante statico la letteratura si concentra su sottoclassi ben delimitate,
il ReDoS~\cite{staicu2018redos} e il costo delle query
GraphQL~\cite{cha2020graphql}; manca invece, per quanto è stato possibile
verificare, un corpo di lavori sottoposti a revisione paritaria sul rilevamento
statico dell'assenza di rate limiting, timeout o limiti di paginazione nel
codice di API REST. Ciò che esiste proviene dalla pratica degli strumenti:
regole sul codice, manifest infrastrutturali e vincoli dichiarati nel contratto
OpenAPI.

Se ne ricava una conclusione sulla natura del segnale statico che distingue
API4 dalle categorie precedenti. In una BOLA l'assenza del controllo nel
gestore coincide con la vulnerabilità, perché il controllo non può risiedere
altrove. Qui la coincidenza si spezza: l'analisi del codice non può affermare
che il difetto esista, dato che il limite potrebbe stare nel gateway o nella
piattaforma di orchestrazione, ma solo che a un dato livello non c'è. È
un'assenza locale, che diventa una segnalazione fondata solo quando un secondo
segnale la conferma; e lo scenario di API9 mostra il caso simmetrico, in cui il
limite presente a un livello non copre tutti gli host
esposti~\cite{owasp2023api9}. La correlazione fra segnali eterogenei non è
dunque un raffinamento dell'analisi, ma la condizione perché un giudizio sia
possibile.

\subsection{API5:2023 -- Broken Function Level Authorization}
\label{subsubsec:api5}

\paragraph{Definizione e collocazione}

Un'API espone operazioni, e non tutte sono destinate a tutti. Creare un invito
con privilegi amministrativi, esportare l'elenco degli utenti, cancellare un
account altrui sono funzioni riservate a un ruolo, e il controllo che verifica
quel ruolo prima di eseguirle è l'autorizzazione a livello di funzione.
API5:2023 raccoglie i casi in cui tale controllo manca o è aggirabile, e un
utente ordinario riesce a invocare funzioni riservate~\cite{owasp2023api5}.

La differenza rispetto ad API1:2023 è di livello, ed è l'unica che OWASP fissi
in modo prescrittivo: nella BOLA l'accesso all'endpoint è previsto e la
violazione avviene manipolando l'identificatore dell'oggetto, mentre se
l'attaccante raggiunge una funzione cui non dovrebbe accedere il caso ricade
sotto la BFLA~\cite{owasp2023api1}. Di fronte a una segnalazione non conta
dunque quali dati siano esposti, ma la legittimità della chiamata: chi legge il
profilo altrui sostituendo un identificatore commette una BOLA, chi invoca
l'esportazione completa degli utenti commette una BFLA. È la forma che la
letteratura chiama escalation verticale~\cite{monshizadeh2014mace}.

Il riferimento tassonomico è CWE-285 \emph{Improper Authorization}, che MITRE
sconsiglia però di usare per mappare vulnerabilità reali, trattandosi di una
classe troppo generica: rimanda piuttosto alle voci figlie, CWE-862 quando il
controllo è assente e CWE-863 quando esiste ma decide male~\cite{cwe285}. La
voce insiste inoltre sulla distinzione fra autorizzazione e autenticazione, che
vale anche qui: un'API può autenticare in modo impeccabile e restare priva di
autorizzazione funzionale. Le relazioni con le altre categorie sono nella
Tabella~\ref{tab:api5_relazioni}.

\paragraph{Cause e meccanismi tecnici tipici}

Il controllo funzionale manca perché non ha un luogo obbligato: OWASP osserva
che l'autorizzazione su una funzione è gestita tramite configurazione oppure a
livello di codice, e che scrivere controlli corretti è confuso, date le molte
gerarchie di ruoli e gruppi delle applicazioni moderne~\cite{owasp2023api5}. Vi
si somma il valore predefinito, perché una rotta aggiunta a un controller eredita
il routing e l'autenticazione, non l'autorizzazione: nasce raggiungibile e tale
resta.

Sfruttarla non richiede manipolazioni. Bastano chiamate legittime verso un
endpoint cui non si dovrebbe accedere, e nelle API il tentativo è più facile
perché la struttura è prevedibile: si sostituisce \texttt{GET} con \texttt{PUT},
oppure \texttt{users} con \texttt{admins}~\cite{owasp2023api5}. La stessa
regolarità che rende un'API documentabile la rende enumerabile.

Il primo scenario lo mostra bene. In un'applicazione ad accesso su invito l'app
mobile chiama \texttt{GET /api/invites/\{invite\_guid\}} e riceve un JSON con
ruolo e indirizzo di posta; l'attaccante ne cambia metodo ed endpoint in
\texttt{POST /api/invites/new}, riservato agli amministratori attraverso una
console priva di controllo di funzione, e si invia un invito con ruolo
\texttt{admin}~\cite{owasp2023api5}. Il controllo, in un certo senso, esisteva:
stava nella console, nel fatto che solo un amministratore vedesse quel pulsante.
Il secondo scenario è più diretto: \texttt{GET /api/admin/v1/users/all}
restituisce i dettagli di tutti gli utenti a chiunque ne indovini il
percorso~\cite{owasp2023api5}.

Tre osservazioni spostano infine il difetto fuori dal singolo gestore. Il
percorso non dice se un endpoint sia amministrativo, perché le funzioni
riservate stanno spesso sotto \texttt{api/users} anziché sotto
\texttt{api/admins}~\cite{owasp2023api5}; i verbi HTTP lasciati abilitati per
inerzia riaprono l'operazione da una via non presidiata~\cite{owasp2023api8}; le
versioni obsolete continuano a servire il gestore precedente al
controllo~\cite{owasp2023api9}.

\paragraph{Impatto}

OWASP colloca l'impatto tecnico nella fascia grave: l'attaccante accede a
funzionalità non autorizzate, le funzioni amministrative sono il bersaglio
privilegiato, e l'esito va dalla divulgazione alla perdita o corruzione dei
dati, fino all'interruzione del servizio~\cite{owasp2023api5}.

Il danno non scala però con il numero di identificatori, bensì con la potenza
della funzione raggiunta. Una BOLA restituisce un record per richiesta, e
l'intera base dati richiede un'enumerazione che nel traffico si vede; una BFLA
su un endpoint di esportazione ottiene lo stesso con una chiamata sola. E poiché
le funzioni riservate sono in prevalenza funzioni di scrittura, il difetto che
espone l'esportazione degli utenti espone, sull'endpoint accanto, la loro
cancellazione.

Conta infine la durata. Il primo scenario non finisce con un dato letto, ma con
un account amministrativo creato attraverso il flusso legittimo
dell'applicazione~\cite{owasp2023api5}: le azioni successive sono
indistinguibili nei registri da quelle di un vero amministratore, e correggere
il difetto non revoca l'account.

\paragraph{Mitigazione}

La prescrizione centrale riguarda il valore predefinito: negare ogni accesso e
richiedere concessioni esplicite ai ruoli per ogni
funzione~\cite{owasp2023api5}. Il vantaggio sta in come si manifesta l'errore:
se il default è il diniego, una dimenticanza produce un \texttt{403} che il
primo test funzionale rivela; se il default è il permesso, la stessa
dimenticanza non produce alcun segnale.

Segue la revisione degli endpoint, da condurre tenendo presenti la logica di
business e la gerarchia dei gruppi~\cite{owasp2023api5}: un lavoro che non
ammette scorciatoie rispetto alla conoscenza del dominio.

La terza raccomandazione è l'unica con una forma sintattica: i controller
amministrativi devono ereditare da un controller astratto che applichi il
controllo in base a ruolo o gruppo~\cite{owasp2023api5}. La misura non aggiunge
verifiche, le riposiziona: il controllo diventa proprietà della gerarchia delle
classi, e ometterlo richiede l'atto deliberato di collocare un gestore fuori da
essa, discontinuità visibile in revisione e cercabile da uno strumento. Nessuna
delle tre risolve però la copertura, perché il controllo protegge solo la
superficie servita dal codice che lo
contiene~\cite{owasp2023api9,owasp2023api8}.

\paragraph{Rilevabilità}

OWASP giudica facile la rilevabilità, perché le API sono strutturate e il modo
di raggiungere una funzione è prevedibile~\cite{owasp2023api5}. Il giudizio
riguarda però metà del problema: formulare la chiamata candidata è facile,
stabilire se la risposta fosse dovuta non lo è, perché un \texttt{200 OK}
attesta che l'operazione è stata eseguita, non che fosse legittimo eseguirla.
Nemmeno il percorso aiuta, come avverte lo stesso documento
OWASP~\cite{owasp2023api5}.

Il contributo della letteratura non è ispezionare il codice ma ricostruire la
specifica mancante. Sun, Xu e Su la ricavano dalla navigazione, dalle pagine
raggiungibili da ciascun ruolo~\cite{sun2011static}; RoleCast dalla forma del
codice, perché dentro una partizione per ruolo i controlli sono applicati in modo
coerente e da quella coerenza si inferisce quali condizioni siano controlli di
sicurezza~\cite{son2011rolecast}; MACE dal contesto di
autorizzazione~\cite{monshizadeh2014mace}. Atlidakis, Godefroid e Polishchuk
rinunciano a inferire e scrivono regole di sicurezza per le API REST,
verificandole con fuzzing stateful~\cite{atlidakis2020checking}; un lavoro
recente affronta lo stesso problema in modalità black box~\cite{liu2025bacscan}.

\subsection{API6:2023 -- Unrestricted Access to Sensitive Business Flows}
\label{subsubsec:api6}

\paragraph{Definizione e collocazione}
Le categorie esaminate finora descrivono controlli assenti. Qui ogni singola
chiamata è legittima: l'utente ha diritto di compierla, i controlli di
autorizzazione funzionano, il codice si comporta come progettato. Il danno
nasce dal numero. OWASP definisce vulnerabile l'endpoint che espone un flusso
di business sensibile senza limitarne adeguatamente l'accesso, portando come
esempi l'acquisto di un prodotto, la creazione di un commento e la prenotazione
di una fascia oraria~\cite{owasp2023api6}.

Segue l'affermazione che definisce davvero la categoria: il rischio di un
accesso eccessivo cambia da settore a settore, e la creazione di post tramite
script può costituire spam per un social network ed essere incoraggiata da un
altro~\cite{owasp2023api6}. Nessuna proprietà del codice, del contratto o
della configurazione rende dunque un endpoint vulnerabile ad API6: lo stesso
identico endpoint è sicuro in un contesto e vulnerabile in un altro, e a
decidere è il modello di business che gli sta dietro.

\paragraph{Cause e meccanismi tecnici tipici}

La causa che OWASP indica non è tecnica: manca una visione d'insieme dell'API
che ne supporti i requisiti di business~\cite{owasp2023api6}. Il difetto
nasce nel raccordo fra chi progetta l'endpoint e chi conosce il valore
economico di ciò che l'endpoint muove, e dove quel raccordo manca nessuno è
nella posizione di accorgersene.

Lo sfruttamento richiede di comprendere il modello di business, individuare i
flussi sensibili e automatizzarne l'accesso~\cite{owasp2023api6}: soltanto
l'ultimo passo produce traffico osservabile. Il primo scenario lo illustra con
una console da gioco annunciata in quantità limitata, acquistata da un
programma eseguito il giorno del lancio e distribuito su indirizzi IP e località
diverse~\cite{owasp2023api6}. La distribuzione geografica non è un dettaglio
di colore: è la contromisura dell'attaccante contro il limite per indirizzo, e
spiega perché il rate limiting nella sua forma più semplice non basti.

\paragraph{Impatto}

Su questo punto il documento OWASP è internamente incoerente: la tabella dei
punteggi classifica l'impatto tecnico come moderato, mentre la descrizione
degli impatti afferma che un impatto tecnico in generale non è atteso e porta
come esempi di danno l'impossibilità per gli utenti legittimi di acquistare un
prodotto e l'inflazione nell'economia interna di un
videogioco~\cite{owasp2023api6}. È la seconda formulazione a corrispondere agli
scenari descritti, che non producono né violazione di riservatezza né
alterazione di dati né indisponibilità del servizio. Ciò che cambia sta fuori
dal sistema e si misura in scorte sottratte, ricavi persi o costi di
acquisizione pagati per utenti inesistenti. Ne segue un effetto collaterale
rilevante: un incidente che non produce indisponibilità né perdita di dati non
attiva le procedure di risposta e viene percepito come problema commerciale
anziché di sicurezza.

\paragraph{Mitigazione}

OWASP propone una struttura a due livelli in cui l'ordine conta: prima si
identificano, sul piano del business, i flussi che un uso eccessivo può
danneggiare, e solo dopo si sceglie il meccanismo tecnico adeguato al rischio
individuato~\cite{owasp2023api6}. Nessuna categoria precedente prescrive una
fase preliminare simile, perché in nessuna altra la configurazione corretta
dipende dall'azienda che la adotta. I meccanismi elencati, dal fingerprinting
del dispositivo al captcha, dall'individuazione di comportamenti non umani come
il passaggio dal carrello all'acquisto in meno di un secondo fino al blocco dei
nodi di uscita Tor, sono presentati come modi per rallentare le minacce
automatizzate, non per impedirle~\cite{owasp2023api6}. La logica che li
accomuna è economica: nessuno produce una decisione binaria affidabile, tutti
spostano il costo dell'attacco fino a superare il profitto atteso.

\paragraph{Rilevabilità}

Il rilevamento automatico si scontra qui con l'assenza di un oracolo: nessun
artefatto analizzabile, che sia codice, contratto o configurazione, risponde
alla domanda se un dato flusso in una data azienda vada protetto, e la mancanza
di una mappatura CWE registra il fatto che non esiste una debolezza del
software da nominare. Le tecniche note per i difetti di logica applicativa
cercano deviazioni da un comportamento
atteso~\cite{felmetsger2010logic,pellegrino2014logic}, mentre qui il flusso
viene percorso correttamente e l'attacco sta nel ripeterlo. Restano le
contromisure comportamentali a runtime indicate da OWASP~\cite{owasp2023api6},
che riconoscono l'automazione durante l'attacco anziché la vulnerabilità prima
che avvenga.

\subsection{API7:2023 -- Server Side Request Forgery}
\label{subsubsec:api7}

\paragraph{Definizione e collocazione}

Nelle categorie viste finora l'attaccante agisce sui dati che l'API restituisce.
In API7:2023 agisce sulle richieste che l'API emette. Il difetto compare quando
un'API recupera una risorsa remota senza validare l'URL fornito dall'utente:
l'attaccante può allora costringere l'applicazione a inviare una richiesta verso
una destinazione inattesa, anche se protetta da un firewall o da una
VPN~\cite{owasp2023api7}. Il server diventa un intermediario involontario, che
agisce per conto di chi lo interroga ma con i propri privilegi di rete. Non
viola quindi un controllo di accesso applicativo: ne annulla uno di rete.

MITRE classifica CWE-918 come debolezza \emph{resultant}, che emerge cioè in
presenza di altre~\cite{cwe918}: l'SSRF è raramente il fine dell'attacco, quasi
sempre il mezzo. A renderla attuale è il contesto in cui le API operano. È più
comune, perché webhook, recupero di file da URL e anteprime dei collegamenti
spingono a raggiungere risorse esterne indicate dall'utente; ed è più
pericolosa, perché fornitori cloud, Kubernetes e Docker espongono canali di
gestione su HTTP a percorsi noti, mentre limitare il traffico in uscita resta
difficile~\cite{owasp2023api7}. I rapporti con le categorie contigue, fra cui la
contromisura condivisa con API10:2023~\cite{owasp2023api10}, sono riassunti
nella Tabella~\ref{tab:api7_relazioni}.

\paragraph{Cause e meccanismi tecnici tipici}

La causa immediata è l'assenza o l'inadeguatezza della validazione dell'URI
fornito dal client, e sono i modelli di sviluppo moderni a incoraggiare
l'accesso a URI di provenienza esterna~\cite{owasp2023api7}. Il difetto nasce
quindi da una funzionalità voluta: nessuno introduce per sbaglio un endpoint che
scarica un'immagine da un indirizzo scelto dall'utente.

I due scenari del documento mostrano le due forme dell'attacco. Nella forma
cieca un social network consente di indicare l'immagine del profilo tramite URL;
l'attaccante scrive \texttt{localhost:8080} nel campo \texttt{picture\_url} e,
misurando il tempo di risposta, deduce se la porta sia aperta, scandendo così la
rete interna~\cite{owasp2023api7}. L'informazione non arriva dal corpo della
risposta, ma dalla sua latenza. Nella forma con ritorno un prodotto di sicurezza
invia una richiesta di prova al webhook che l'utente sta configurando e gliene
mostra la risposta; l'attaccante vi indica il servizio di metadati dell'ambiente
cloud e ne ottiene le credenziali~\cite{owasp2023api7}. Il webhook rende comune
il difetto, l'indirizzo di metadati a percorso noto lo rende grave.

Una terza famiglia riguarda non l'assenza della validazione ma il suo
aggiramento --- formati alternativi di un indirizzo IP, redirezioni verso host
interni, schemi come \texttt{file://}~\cite{cwe918}. Validare un URL è insomma
un problema di parsing, che le espressioni regolari scritte a mano risolvono
male. Un'analisi su oltre 27.000 applicazioni PHP mostra però che la
causa più diffusa non è una difesa mal costruita, ma l'assenza di qualunque
difesa~\cite{wessels2024ssrf}.

\paragraph{Impatto}

OWASP elenca come esiti l'enumerazione dei servizi interni per scansione di
porte, la divulgazione di informazioni, l'aggiramento di firewall e, in alcuni
casi, il denial of service o l'uso del server come proxy~\cite{owasp2023api7}.

L'elemento che distingue l'SSRF è il cambio di perimetro: l'attaccante non
ottiene un dato, ottiene una posizione, quella del server. Il valore
dell'attacco dipende perciò da cosa sia raggiungibile dall'interno: in
un'architettura piatta un solo endpoint vulnerabile annulla la protezione di
tutti i servizi che si fidano del perimetro, in una segmentata consente poco più
di una scansione.

I servizi di metadati cloud convertono poi l'SSRF da ricognizione a
compromissione: rispondono a un indirizzo fisso e noto, non richiedono
autenticazione perché presuppongono che solo l'istanza possa raggiungerli, ed
espongono le credenziali del ruolo associato alla macchina, e MITRE ne registra
casi sfruttati attivamente~\cite{cwe918}.

\paragraph{Mitigazione}

Sul piano della rete OWASP raccomanda di isolare il meccanismo di recupero delle
risorse, che di norma mira a risorse remote e non interne~\cite{owasp2023api7}.
È la difesa più robusta perché non dipende dalla correttezza della validazione:
se il componente che effettua le richieste in uscita non ha rotta verso la rete
interna, un URL malevolo non produce nulla.

Sul piano applicativo il documento prescrive liste di elementi ammessi su tre
dimensioni --- origini remote attese, schemi di URL e porte, tipi di media
accettati~\cite{owasp2023api7} --- ciascuna delle quali blocca una famiglia di
aggiramenti diversa. Seguono la disabilitazione delle redirezioni, un parser di
URL collaudato e il divieto di restituire al client le risposte
grezze~\cite{owasp2023api7}: quest'ultima misura non impedisce l'attacco, ma ne
degrada l'esito dalla forma con ritorno a quella cieca.

Va infine registrata un'ammissione che nessun'altra categoria contiene: il
rischio SSRF non può sempre essere eliminato del tutto~\cite{owasp2023api7},
perché funzionalità e vulnerabilità coincidono. Un servizio che offre anteprime
di collegamenti arbitrari deve per definizione contattare indirizzi scelti
dall'utente: se ne può confinare l'effetto, non eliminare il comportamento che
lo rende possibile.

\paragraph{Rilevabilità}

Per la prima volta nel capitolo le due fonti primarie concordano, e a favore
dell'analisi statica. OWASP giudica facile la rilevabilità, con la sola
eccezione della forma cieca~\cite{owasp2023api7}; CWE-918 indica come metodo
l'analisi statica automatica --- la ricerca dei percorsi che collegano una
sorgente di input a un sink --- e ne dichiara alta l'efficacia~\cite{cwe918}.
Il motivo è che qui l'oracolo è interno al codice: per API4 e API5 lo strumento
osserva l'assenza di un controllo senza poter sapere se fosse dovuto, mentre per
API7 la domanda non è se qualcosa manchi, ma se due punti del programma siano
connessi, proprietà verificabile senza conoscere le intenzioni del progettista.

La letteratura conferma il quadro e ne segnala i limiti ricorrenti: un'analisi
di flusso su codice PHP validata manualmente~\cite{wessels2024ssrf}, la potatura
dei percorsi non sfruttabili per contenere i falsi positivi~\cite{ji2025artemis},
il fuzzing affiancato alla marcatura dinamica~\cite{wang2024ssrfuzz}. Se ne
ricavano tre problemi che anche il modulo descritto nella parte sperimentale
deve affrontare: l'inventario dei sink, dato che ometterne uno produce un falso
negativo silenzioso; la sovra-marcatura, perché non ogni stringa contaminata che
raggiunge un sink produce un URL controllabile; la validazione intermedia, dove
distinguere un controllo efficace da uno aggirabile richiede di ragionarne la
semantica.

Resta la verifica dinamica, sulla quale ricade la distinzione fra le due forme.
Con ritorno la conferma è immediata: si punta l'endpoint verso un indirizzo
controllato e si osserva se la richiesta arriva; per la forma cieca serve un
canale laterale, tipicamente una risoluzione DNS. Nella pipeline adottata nel
seguito la mancata conferma non declassa quindi la segnalazione statica, perché
indica soltanto che il canale di ritorno non è stato osservato.

\subsection{API8:2023 -- Security Misconfiguration}
\label{subsubsec:api8}

\paragraph{Definizione e collocazione}

Le categorie viste finora individuano un difetto in un punto preciso: un
controllo che manca, un limite non impostato, un URL non validato. API8:2023 non
ha un punto. OWASP dichiara che la configurazione insicura può verificarsi a
qualunque livello dello stack, dalla rete all'applicazione, e i suoi otto
indicatori attraversano tutti quei livelli, dall'hardening assente ai verbi HTTP
lasciati abilitati, dal TLS mancante ai messaggi di errore che espongono tracce
dello stack~\cite{owasp2023api8}. Hanno una sola cosa in comune: nessuno è un
errore di logica applicativa. Il codice fa quello che deve; è l'ambiente in cui
gira a produrre l'esposizione.

La particolarità tassonomica lo conferma. OWASP associa alla categoria sette
voci CWE, più di qualunque altra della Top~10, ma diverse non sono debolezze:
CWE-16 \emph{Configuration} è una categoria di cui MITRE dichiara proibita la
mappatura, indicando di analizzare piuttosto il comportamento che la
configurazione ha determinato~\cite{cwe16}. Se ne ricava il criterio: la
configurazione non è una debolezza, è il meccanismo attraverso cui una debolezza
viene introdotta. Una politica CORS permissiva non è insicura in astratto, lo
diventa perché produce un difetto di controllo di accesso.

Le metriche collocano API8 fra le voci più gravi: sfruttabilità facile,
prevalenza diffusa, rilevabilità facile, impatto tecnico
severo~\cite{owasp2023api8}. Gli attaccanti cercano difetti non corretti e
servizi con impostazioni predefinite insicure, informazioni in larga parte di
pubblico dominio~\cite{owasp2023api8}: non serve comprendere l'applicazione,
serve sapere che cosa cercare. Le sovrapposizioni con le categorie contigue
sono nella Tabella~\ref{tab:api8_relazioni}.

\paragraph{Cause e meccanismi tecnici tipici}

La causa strutturale è che la configurazione non risiede in un luogo unico né
sotto una responsabilità unica: si distribuisce fra codice, file di
orchestrazione, gateway, impostazioni cloud e valori predefiniti delle librerie,
ciascuno con un ciclo di vita proprio. Un valore corretto al rilascio può
cessare di esserlo dopo un aggiornamento che nessuno ha collegato alla
sicurezza.

Il primo scenario mostra il predefinito pericoloso, ed è riconoscibilmente il
caso Log4Shell. Un'utilità di logging diffusa supporta le ricerche JNDI,
abilitate per impostazione predefinita; l'attaccante invia una richiesta verso
\texttt{/health} con un'intestazione contenente un riferimento JNDI a un server
LDAP che controlla, e quando l'utilità espande quel valore per scriverlo nel
registro scarica ed esegue l'oggetto malevolo~\cite{owasp2023api8}. Nella catena
non c'è alcun difetto del codice applicativo.

Il secondo mostra il meccanismo opposto, l'impostazione assente: un social
network espone i messaggi privati tramite \path{/dm/user_updates.json} e, non
inviando l'intestazione \texttt{Cache-Control}, lascia che le conversazioni
finiscano nella cache del browser~\cite{owasp2023api8}. Qui non c'è nulla da
disabilitare, c'è una direttiva che nessuno ha inviato. Resta poi la causa più
diffusa, che l'elenco mette al secondo posto: patch mancanti e sistemi non
aggiornati~\cite{owasp2023api8}, difetto di manutenzione più che di
configurazione.

\paragraph{Impatto}

Le configurazioni insicure, scrive OWASP, non solo espongono dati sensibili
degli utenti, ma anche dettagli del sistema che possono condurre alla
compromissione completa del server~\cite{owasp2023api8}. È la seconda parte a
giustificare l'impatto severo, e i due scenari ne mostrano gli estremi:
conversazioni private da un lato, esecuzione di codice arbitrario dall'altro.

Ciò che distingue API8 è però la natura abilitante del difetto, che raramente
costituisce l'attacco e quasi sempre la condizione che ne rende praticabile un
altro. Una traccia di stack non compromette nulla di per sé, ma rivela versioni e
percorsi interni e abbassa il costo della ricognizione; una politica di uscita
permissiva trasforma un SSRF cieco in uno con ritorno. Vi si aggiunge l'ampiezza:
essendo trasversale, un difetto di configurazione non riguarda un endpoint ma
tutti quelli serviti da quel componente.

\paragraph{Mitigazione}

Sul piano del processo OWASP chiede un procedimento di hardening ripetibile, una
revisione delle configurazioni sull'intero stack e un processo automatizzato che
ne valuti l'efficacia in tutti gli ambienti~\cite{owasp2023api8}. I tre
requisiti hanno un'implicazione comune che conviene rendere esplicita: la
configurazione va trattata come artefatto versionato e verificabile, non come
stato accumulato di una macchina.

Sul piano dei controlli le sei misure elencate riguardano il canale cifrato
verso ogni componente, i verbi HTTP da restringere, la politica CORS e le
intestazioni di sicurezza, i tipi di contenuto accettati, l'elaborazione
uniforme delle richieste lungo la catena e gli schemi dei payload di risposta,
comprese quelle di errore~\cite{owasp2023api8}. Due meritano una nota: il canale
cifrato è prescritto anche per le API interne, il che chiude l'assunto per cui il
traffico interno sarebbe fidato; e lo schema dichiarato per le risposte di errore
non è documentazione, ma un vincolo che a runtime impedisce la fuga di
informazioni diagnostiche.

\paragraph{Rilevabilità}

OWASP classifica la rilevabilità come facile con una motivazione che, per la
prima volta nel capitolo, rinvia agli strumenti: ne esistono di automatici per
individuare e sfruttare configurazioni errate~\cite{owasp2023api8}. La
formulazione è simmetrica: gli stessi strumenti servono a chi difende e a chi
attacca, perché ciò che cercano è pubblicamente noto.

La ragione per cui il rilevamento funziona si comprende per contrasto. Per
l'autorizzazione funzionale lo strumento non sapeva se un controllo fosse dovuto;
per il consumo di risorse non sapeva se un limite fosse applicato altrove. Per la
configurazione l'oracolo è esterno e pubblico --- valori raccomandati,
predefiniti noti come pericolosi, versioni vulnerabili --- e verificare la
conformità a un riferimento è un problema di confronto, non di inferenza.

Restano tre limiti. La copertura: ciò che non è dichiarato in un file non è
ispezionabile prima dell'esecuzione. La deriva: un'analisi statica attesta ciò
che un file dichiara, non ciò che è attivo sul sistema. Il contesto: una politica
CORS che ammette qualunque origine è un difetto per un'API a client autenticati e
una scelta legittima per un'API pubblica di sola lettura, sicché la verifica
sintattica non stabilisce se un'impostazione sia sbagliata, ma solo se si
discosta da un riferimento la cui pertinenza dipende dall'endpoint.

Va infine notata la natura del segnale. Per le categorie di autorizzazione
l'analisi cerca l'assenza di qualcosa che avrebbe dovuto esserci; per API8 cerca
la presenza di qualcosa che non avrebbe dovuto esserci, o l'assenza di qualcosa
che ha un valore corretto noto. Il secondo problema si presta al confronto e
produce falsi positivi contestuali ma pochi falsi negativi; il primo richiede di
ricostruire l'intenzione del progettista.

\subsection{API9:2023 -- Improper Inventory Management}
\label{subsubsec:api9}

\paragraph{Definizione e collocazione}

Le categorie viste finora descrivono un difetto in qualcosa che l'organizzazione
sa di avere: un handler, un limite, una configurazione. API9:2023 riguarda ciò
che non sa di avere. Il difetto non è nel codice ma nella visibilità, e OWASP lo
definisce come scarsa catalogazione degli host e delle versioni di un'API,
articolandolo in due punti ciechi~\cite{owasp2023api9}.

Il primo è quello della documentazione: restano senza risposta esplicita le
domande su quale ambiente ospiti un'API, chi debba avervi accesso di rete e quale
versione sia in esecuzione, la documentazione manca o è obsoleta, e non esistono
né un piano di dismissione né un inventario aggiornato degli
host~\cite{owasp2023api9}. Il secondo è quello dei flussi di dati, e ricorre
quando dati sensibili raggiungono terze parti senza motivazione di business,
approvazione o visibilità su cosa venga condiviso~\cite{owasp2023api9}.

Il riferimento tassonomico conferma la particolarità della categoria. OWASP
rinvia a CWE-1059, di cui MITRE dichiara proibita la mappatura~\cite{cwe1059}: è
la seconda volta nell'elenco, dopo CWE-16 per API8, che la voce di riferimento
non serve a classificare una vulnerabilità reale. Qui però non è
un'imprecisione della tassonomia, bensì una proprietà della categoria, perché
l'assenza di un inventario non è un comportamento del prodotto. Le metriche sono
sfruttabilità facile, prevalenza diffusa, rilevabilità media e impatto tecnico
moderato~\cite{owasp2023api9}.

\paragraph{Cause e meccanismi tecnici tipici}

La causa è un'asimmetria fra due costi: esporre una nuova istanza richiede pochi
minuti, catalogarla e prevederne la dismissione richiede un processo che nessuna
pipeline esegue da sola. Ogni ambiente di collaudo è però un'API completa e
raggiungibile, mentre l'inventario che dovrebbe elencarlo è un documento
aggiornato a mano.

Il primo scenario ne mostra la conseguenza. Un social network protegge il
recupero della password dalla forza bruta, ma il meccanismo non è nel codice
dell'API: risiede in un componente interposto fra il client e l'host ufficiale.
Un ricercatore individua \path{beta.api.socialnetwork.owasp.org}, che esegue la
stessa API senza esserne coperto, e reimposta la password di qualunque utente
indovinando un token di sei cifre~\cite{owasp2023api9}. Il controllo esisteva ed
era corretto: non copriva tutti gli host che servivano quel codice.

Il secondo scenario riguarda l'altro punto cieco: un'applicazione malevola
ottiene il consenso di 270.000 utenti ma, attraverso di essi, accede alle
informazioni private di 50.000.000 di contatti, per assenza di restrizioni e
monitoraggio sui flussi~\cite{owasp2023api9}. Qui non c'è alcun host
dimenticato: manca la conoscenza di dove i dati finiscano.

\paragraph{Impatto}

OWASP classifica l'impatto tecnico come moderato, osservando che gli attaccanti
possono ottenere accesso non autorizzato a dati sensibili o compromettere i
server~\cite{owasp2023api9}. Il dettaglio decisivo è però che versioni diverse
della stessa API sono talvolta collegate alla medesima base di
dati~\cite{owasp2023api9}: l'host dimenticato non è una copia isolata, è una
seconda porta sugli stessi dati.

Ne discende il tratto distintivo. API9 non introduce una vulnerabilità propria:
rende raggiungibili quelle altrui e ne impedisce la correzione, perché una patch
si applica a ciò che si sa di avere in esecuzione. Il giudizio di impatto
moderato è quindi fuorviante: la gravità effettiva è quella del difetto peggiore
che l'host non inventariato continua a servire.

\paragraph{Mitigazione}

Le contromisure muovono tutte dallo stesso presupposto, che la visibilità vada
prodotta e non presupposta~\cite{owasp2023api9}. Le prime sono di inventario ---
gli host, con ambiente, accesso di rete e versione, e i servizi integrati, con
ruolo e sensibilità dei dati --- cui segue la documentazione dell'API, che deve
coprire autenticazione, errori, redirezioni, limitazione di frequenza, politica
CORS ed endpoint.

La misura più incisiva è però la successiva: generare la documentazione in modo
automatico, con standard aperti e dentro la pipeline di integrazione
continua~\cite{owasp2023api9}. La differenza non è di grado ma di natura, perché
trasforma la documentazione da documento parallelo, che diverge appena qualcuno
dimentica di aggiornarlo, in artefatto prodotto dalla compilazione.

Restano tre prescrizioni sulle versioni: applicare le misure di sicurezza
esterne a tutte quelle esposte e non alla sola produzione, che è ciò che il primo
scenario mostra disatteso; non usare dati di produzione fuori dalla produzione; e
decidere, quando una versione nuova porta miglioramenti di sicurezza, se
riportarli sulle precedenti o imporre la migrazione~\cite{owasp2023api9}.

\paragraph{Rilevabilità}

OWASP giudica media la rilevabilità e non indica un metodo, limitandosi a
osservare che una documentazione obsoleta rende più difficile individuare e
correggere le vulnerabilità~\cite{owasp2023api9}. L'osservazione descrive un
difetto che ostacola il proprio rilevamento: l'artefatto che servirebbe a
trovarlo è quello che manca.

Ciò che si può fare per via automatica è un confronto fra rappresentazioni. Le
rotte implementate nel codice ma non dichiarate nel contratto sono candidate a
essere API ombra, raggiungibili ma ignote a ogni revisione basata sulla
specifica; quelle dichiarate ma non implementate segnalano documentazione
obsoleta. Nessuna delle due è una vulnerabilità, ma entrambe misurano la
divergenza fra il modello e la realtà.

Il confronto ha però un limite intrinseco: opera fra due rappresentazioni della
stessa applicazione e non dice nulla sugli host su cui essa è distribuita. Il
primo scenario è precisamente il caso in cui codice e contratto coincidono e il
difetto sta nella topologia di rete, il che richiede ricognizione
infrastrutturale e non analisi del software.

La letteratura sottoposta a revisione paritaria è qui scarsa: non esiste un
insieme di verità di riferimento contro cui misurare un rilevatore di API
ombra, perché costruirlo richiederebbe l'inventario completo di organizzazioni
reali, cioè proprio l'informazione che per ipotesi manca. Per API9 non esiste
dunque un rilevamento nel senso in cui esiste per le altre categorie, cioè
l'individuazione di un difetto dentro un artefatto: esiste la misura di una
divergenza fra rappresentazioni indipendenti dello stesso sistema ---
contratto, codice, inventario, traffico --- il cui valore non sta nel produrre
un verdetto, ma nel restituire la visibilità che il difetto sottrae.

\subsection{API10:2023 -- Unsafe Consumption of APIs}
\label{subsubsec:api10}

\paragraph{Definizione e collocazione}

Le nove categorie esaminate finora descrivono tutte l'API come bersaglio di un
attacco diretto. API10:2023 rovescia la prospettiva: l'attaccante non colpisce
l'API bersaglio ma un servizio da cui essa dipende, e il danno arriva per un
canale che l'applicazione considera fidato. Le note di rilascio dichiarano di
aver introdotto la categoria perché gli attaccanti hanno cominciato a
compromettere i servizi integrati anziché le API del
bersaglio~\cite{owasp2023apireleasenotes}.

La causa che OWASP individua è psicologica prima che tecnica: gli sviluppatori
si fidano dei dati ricevuti da terze parti più di quanto si fidino dell'input
dell'utente, e adottano standard più deboli quanto a trasporto, autenticazione e
validazione~\cite{owasp2023api10}. Le cinque condizioni di vulnerabilità sono
canale non cifrato, dati non validati, redirezioni seguite ciecamente, risorse
non limitate e timeout assenti~\cite{owasp2023api10}; nel repository
pubblico del progetto è stata sollevata, senza esito, l'obiezione che almeno tre
di esse ricadano in altre categorie~\cite{owasp2023apiissue80}.

I riferimenti esterni sono generici --- CWE-20, CWE-200 e CWE-319 --- ma la
genericità riflette una proprietà reale: l'impatto varia a seconda di ciò che
l'API bersaglio fa con i dati prelevati~\cite{owasp2023api10}, sicché la
debolezza dipende dalla destinazione del dato. API10 individua un punto
d'ingresso, non un difetto terminale. I rapporti con le categorie contigue sono
nella Tabella~\ref{tab:api10_relazioni}.

\paragraph{Cause e meccanismi tecnici tipici}

La causa strutturale è un confine di fiducia collocato nel punto sbagliato. Un
servizio di terze parti occupa una posizione ambigua: è esterno
all'applicazione, ma scelto deliberatamente, raggiungibile su un canale che essa
ha configurato e spesso offerto da un'azienda reputata affidabile. La sua
risposta attraversa così un confine che nessuno ha presidiato, perché nessuno lo
ha riconosciuto come tale.

Il primo scenario mostra l'iniezione differita. Un'API si affida a un servizio
esterno per arricchire gli indirizzi commerciali degli utenti e ne salva i dati
in una base di dati SQL; gli attaccanti vi memorizzano un payload di SQL
injection associato a un'attività creata da loro, poi inducono l'API a
prelevarla~\cite{owasp2023api10}. Ciò che lo distingue da un'iniezione ordinaria
è che l'attaccante non invia mai il payload all'API bersaglio: lo deposita
altrove, e sanificare l'input degli utenti non serve, perché quell'input è un
innocuo nome di attività.

Il secondo scenario mostra la redirezione seguita ciecamente. Un'API invia
informazioni mediche a un fornitore su connessione cifrata; gli attaccanti lo
compromettono ed esso risponde con un \texttt{308 Permanent Redirect}, sicché
l'API ripete la richiesta identica, dati sensibili compresi, verso il loro
server~\cite{owasp2023api10}. La fuga avviene per un comportamento predefinito
del client HTTP che nessuno ha valutato come decisione di sicurezza.

Il terzo scenario è il più istruttivo, perché la terza parte non deve nemmeno
essere compromessa: un attaccante crea un repository Git denominato
\path{'; drop db;--}, e l'applicazione che vi si integra ne usa il nome per
costruire una query SQL ritenendolo sicuro~\cite{owasp2023api10}. Il servizio ha
restituito fedelmente il nome scelto dal proprio utente; è l'applicazione ad aver
confuso l'autenticità del canale con l'affidabilità del contenuto. Un servizio
terzo può dunque veicolare dati malevoli perché compromesso, perché usato come
deposito, o perché trasmette contenuti altrui: solo il primo caso richiede
un'intrusione.

\paragraph{Impatto}

L'impatto varia a seconda di ciò che l'API bersaglio fa con i dati prelevati:
esposizione di informazioni sensibili, molti tipi di iniezione o denial of
service~\cite{owasp2023api10}. È classificato come severo, e i tre scenari ne
coprono tre punti: esfiltrazione, fuga di dati sanitari, distruzione di dati.

Ciò che caratterizza la categoria è che il difetto non ne determina l'entità:
questa è funzione di dove il dato non validato finisce. Un'informazione prelevata
da un fornitore e memorizzata può essere riletta mesi dopo da un componente che
la tratta come dato interno, perché proviene dalla base di dati
dell'organizzazione. Vi si aggiunge la scala, perché compromettere un solo
fornitore raggiunge tutte le applicazioni che lo integrano.

\paragraph{Mitigazione}

OWASP elenca quattro contromisure~\cite{owasp2023api10}: valutare la postura di
sicurezza dei fornitori al momento della scelta, imporre un canale di trasporto
sicuro, validare e sanificare i dati ricevuti dalle API integrate, mantenere una
lista delle posizioni verso cui esse possono redirigere. La terza è il nucleo
della categoria ed è formulata negli stessi termini riservati all'input
dell'utente: la contromisura consiste nell'abolire la distinzione fra le due
sorgenti. Due delle cinque condizioni --- timeout e limiti sulle risposte ---
restano però prive di contromisura corrispondente. Quando il contratto del
fornitore è noto, la risposta può essere validata rispetto a uno schema: il
controllo non intercetta un payload conforme, ma trasforma la fiducia implicita
in un vincolo dichiarato.

\paragraph{Rilevabilità}

OWASP classifica la rilevabilità come media senza indicare come procedere,
limitandosi a osservare che l'attaccante deve identificare i servizi con cui il
bersaglio si integra ed eventualmente comprometterli~\cite{owasp2023api10}.

Sul piano statico il problema è di configurazione più che di tecnica. L'analisi
della contaminazione richiede un insieme di sorgenti e uno di destinazioni, e per
convenzione consolidata le sorgenti sono i punti in cui entra l'input
dell'utente; per API10 la sorgente è invece il valore restituito da una chiamata
HTTP in uscita. Un motore configurato secondo quella convenzione non lo considera
contaminato, e un flusso dalla risposta di un fornitore a una query SQL non
produce segnalazione, benché sia identico a uno che partisse da un parametro di
richiesta. Due dei cinque difetti si prestano invece a un rilevamento diretto,
perché basta osservare la configurazione locale della chiamata: la redirezione
seguita per impostazione predefinita e il timeout mancante, dove il segnale non è
la presenza di un'opzione errata ma l'assenza di un'opzione che disattivi il
predefinito insicuro.

Sul piano dinamico la verifica è ostacolata da un problema di controllo: provare
che un'applicazione accetti dati malevoli richiede che il fornitore li
restituisca, il che è possibile solo se il servizio consente di immettervi
contenuti oppure sostituendolo con un doppio in collaudo, che però verifica
l'applicazione e non l'integrazione reale. La letteratura dedicata alla categoria
è pressoché assente, per quanto è stato possibile verificare: i lavori sulla
catena di fornitura riguardano le dipendenze da pacchetti, quelli sulla
contaminazione assumono la convenzione appena discussa, e il caso dell'API che si
fida di un'altra API si colloca fra i due.
